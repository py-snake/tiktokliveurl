## HIGH

### H1. Corrupted localStorage JSON crashes the entire app
**`index.php:616`**  
`let profiles = JSON.parse(localStorage.getItem('tt_profiles') || '{}');` — if stored JSON is corrupted (browser crash, manual edit, truncation), `JSON.parse` throws an uncaught `SyntaxError` at top-level scope. The `profiles` variable is never assigned; every subsequent function (`renderCards`, `saveProfiles`, `refreshProfile`) throws `TypeError`. **The app is bricked until the user manually clears localStorage.** Needs a `try/catch` wrapping the parse with a fallback to `{}`.

### H2. DoS via unbounded FLV worker hold
**`proxy.php:245-261`**  
The FLV branch sets `set_time_limit(0)` and `CURLOPT_TIMEOUT => 0`. While `CURLOPT_LOW_SPEED_LIMIT` and `connection_aborted()` provide stall/disconnect protection, an attacker who opens many connections and reads just enough to pass the low-speed threshold — then stalls — holds a PHP-FPM worker indefinitely. On serv00's 3-worker pool, **3 stalled connections exhaust all workers**, making even `index.php` unreachable. No per-connection request limit exists.

### H3. SSL certificate verification disabled everywhere
**`api.php:491-492`, `proxy.php:143-144`, `proxy.php:183-184`, `proxy.php:268-269`**  
Every outbound HTTPS request (all TikTok API calls and all CDN streams) uses `CURLOPT_SSL_VERIFYPEER => false` + `CURLOPT_SSL_VERIFYHOST => false`. An attacker who can MITM the connection (shared hosting network, DNS hijack) can intercept all TikTok API traffic, inject fake room status, and read stream URLs in transit.

## MEDIUM

### M1. Token not escaped in JavaScript output
**`index.php:613`**  
```php
const TOKEN = '<?= $token ?>';
```
The master token is echoed into a `<script>` block without `json_encode()` or any JS escaping. Currently harmless (UUID format), but violates defense-in-depth — any future token format with `'`, `</script>`, etc. becomes XSS. Fix: `<?= json_encode($token) ?>`.

### M2. Token leaked in query strings and server logs
**`index.php:613,963`**, **`api.php:19`**, **`proxy.php:14,216-224`**  
The token appears in page source (DevTools), proxy URLs sent to flv.js/hls.js (player error logs, browser history), HLS playlist segment URLs (re-fetched by player), and server access logs. An attacker with access to logs, browser history, or network traces can steal the token.

### M3. CORS wildcard on proxy.php
**`proxy.php:32`**  
`Access-Control-Allow-Origin: *` on all successful responses. Combined with the token being in the URL (M2), any malicious page loaded by the token holder can silently proxy TikTok streams cross-origin.

### M4. No rate limiting on api.php
**`api.php` (entire file)**  
Zero rate limiting. Each `check` action triggers up to 4 outbound HTTP requests to TikTok. An attacker with a valid token can flood the endpoint and exhaust serv00's 3-worker pool.

### M5. HLS regex only matches `.ts` segments
**`proxy.php:216`**  
`/^(?!#)(.+\.ts.*)$/m` — if TikTok switches to CMAF/fMP4 segments (`.mp4`, `.m4s`), all segment URLs are silently dropped from the rewritten playlist. The m3u8 would parse as empty. Currently fine but fragile for the future.

### M6. Double URL decode in proxy.php
**`proxy.php:43`**  
`$_GET['url']` is already URL-decoded by PHP. The explicit `urldecode()` performs a second decode. A URL containing `%26` (encoded `&`) becomes a raw `&`, splitting the query string. A URL containing `%252e%252e%252f` becomes `../` after double-decode. The CDN allowlist mitigates path traversal, but the double-decode is a correctness bug for URLs with percent-encoded characters.

### M7. renderCards() does full innerHTML rebuild on every update
**`index.php:877`**  
`container.innerHTML = usernames.map(...).join('')` — destroys and recreates ALL card DOM elements every time any profile is refreshed. Causes: scroll position loss, avatar image re-loading, availability check restarts, visible layout flicker. With 50 profiles and sequential refresh, `renderCards()` is called 50+ times per cycle.

### M8. refreshAll() re-enters from timer without concurrency guard
**`index.php:731,753`**  
With `POOL=1`, 50 profiles take ~150-250s. `setInterval(refreshAll, 60000)` fires again before the previous run completes. Two concurrent refresh loops race on the shared `profiles` object, cause duplicate API calls, and trigger interleaved `renderCards()` calls → flicker.

### M9. HLS.js fatal error doesn't destroy the instance
**`index.php:1101-1103`**  
```js
hls.on(Hls.Events.ERROR, (event, data) => {
    if (data.fatal) status.textContent = `Playback error: ${data.details || data.type}`;
});
```
Per HLS.js docs, fatal errors require calling `hls.destroy()`. Without it, the instance continues emitting errors and leaking memory. The player stays in a broken state.

### M10. Safari native HLS has no error handler
**`index.php:1106-1111`**  
The native HLS path sets `video.src` and listens for `loadedmetadata`, but has no `video.addEventListener('error', ...)`. If the CDN is down, the video silently fails — status stays at "Loading..." forever with no user feedback.

### M11. Autoplay rejection silently swallowed
**`index.php:1099, 1110, 1124`**  
`video.play().catch(() => {})` silently swallows `NotAllowedError`. The user sees "Loading..." disappear but the video stays paused with no explanation. Should show "Click the video to play" or similar.

### M12. saveProfiles() QuotaExceededError caught as wrong error
**`index.php:683,713,842`**  
When localStorage is full:
- `checkUser()` (line 683): caught → shows **"Network error. Please try again."** — misleading
- `refreshProfile()` (line 713): caught → silently lost
- `removeProfile()` (line 842): **not wrapped in try/catch** → uncaught exception

### M13. Denied notification permission shows "enabled" toast
**`index.php:760-777`**  
If permission is `denied`, the prompt is skipped but `showToast('Browser notifications enabled')` still fires. The user thinks notifications work but they silently never fire.

### M14. Two browser tabs overwrite each other's localStorage
**`index.php:616,848-849`**  
Both tabs have independent in-memory `profiles`. If Tab A adds a profile while Tab B refreshes, Tab B's stale snapshot overwrites Tab A's change on `saveProfiles()`. No cross-tab sync mechanism.

### M15. CORS headers missing on proxy.php error responses
**`proxy.php:16-73,196-199,312-314`**  
6 out of 8 exit points lack the CORS header (401, 400, 403, HLS 502, FLV 502). Browser-based callers can't read error responses cross-origin. Low impact for current same-origin usage, but breaks third-party integrations.

### M16. No Content-Type header on proxy.php error responses
**`proxy.php:16-73,196-199,312-314`**  
Error paths echo plain text without setting `Content-Type: text/plain`. Browsers may misinterpret the response.

### M17. api.php worst-case serial timeout is 40s
**`api.php:461-517`**  
A single `check` action makes up to 4 sequential HTTP calls (room ID from API, room ID from HTML, alive check, room info), each with a 10s timeout. Worst case: 40s per check. On serv00's 3-worker pool, this is a worker held for 40s.

### M18. 3-worker pool exhaustion
**`proxy.php:245-309`, `api.php`**  
One FLV stream + one HEAD check + one API check = all 3 workers consumed. A 4th request queues indefinitely. The frontend's `POOL=1` helps but doesn't prevent external requests or concurrent tabs.

## LOW

### L1. Curl error message leaked to client
**`proxy.php:314`**  
`echo 'Upstream error' . ($curlError ? ": $curlError" : '')` — reveals internal DNS names, network topology, or proxy configuration in error messages.

### L2. Cookie secure flag conditional on server configuration
**`index.php:13`**  
`'secure' => !empty($_SERVER['HTTPS']) && $_SERVER['HTTPS'] !== 'off'` — on shared hosting behind a reverse proxy, this variable may not be set correctly, causing the cookie to be sent over HTTP.

### L3. No concurrency guard on refreshAll() overlap
**`index.php:722-747`**  
Manual "Refresh Now" click + interval timer can run two `refreshAll()` concurrently. The sequential `POOL=1` helps but interleaving still causes wasted API calls.

### L4. last-refresh timestamp updates on failure
**`index.php:746`**  
The timestamp updates even when all profiles fail to refresh, giving the user a misleading sense of freshness.

### L5. Modal has no ARIA attributes or focus trap
**`index.php:598-607`**  
Missing `role="dialog"`, `aria-modal="true"`, and focus trap. Tab can move focus out of the modal.

### L6. Undersized touch targets
**`index.php:394,462`**  
`.player-close` padding 4px/8px, `.btn-remove` padding 8px/12px — below the 44x44px WCAG minimum.

### L7. Availability check results wasted on stale DOM
**`index.php:1053-1058`**  
After `renderCards()` rebuilds the DOM, pending availability check callbacks reference old button IDs. The `if (!btn) return` guard prevents a crash but the check was wasted work.

### L8. api.php `parseStreamUrls` — missing `sdk_key` emits PHP warning
**`api.php:427`**  
If a quality entry is missing `sdk_key`, `$q['sdk_key']` emits a PHP 8.x warning and creates a null key in `$levelMap`.

### L9. Corrupt gzip in HLS branch serves garbage m3u8
**`proxy.php:204-208`**  
If gzip magic bytes match but data is corrupt, `@gzdecode()` returns `false` (warning suppressed) and the corrupt body is used as the m3u8. Rewritten URLs would be garbage.

### L10. URL with no scheme produces invalid segment URLs
**`proxy.php:221`**  
If the input URL has no scheme (e.g., `//host/path`), `parse_url()` omits `scheme`, producing `://host/path/segment.ts`. Theoretical — all TikTok URLs use `https://`.

### L11. HLS rewrite passes absolute non-CDN URLs (caught on re-fetch)
**`proxy.php:218-219`**  
If a segment line is `http://evil.com/seg.ts`, the m3u8 rewrite includes it as-is. The proxy re-validates the host on the subsequent fetch, so it's caught — but the m3u8 content is poisoned until then.

### L12. tiktok short URLs (vm.tiktok.com/Zxxx) not handled
**`api.php:92`**  
`extractUsername()` regex only matches `tiktok.com/@user` patterns. Short URLs like `vm.tiktok.com/Zxxx` pass through and fail at room-ID lookup with a confusing error.

### L13. Debug field inconsistently present in check response
**`api.php:113`**  
The `debug` key only appears on room-ID resolution failure, not on success. Inconsistent API response shape.

### L14. API has no version prefix
**`api.php` (entire file)**  
No `/v1/` or similar versioning. Future breaking changes risk existing clients.

### L15. HEAD probe 12s timeout may false-negative in slow CDN regions
**`proxy.php:119`**  
Akamai edge nodes in Asia-Pacific can take 15s+ during peak hours. The 12s timeout may incorrectly report "unavailable" for working streams.

### L16. escHtml() doesn't escape single quotes
**`index.php:1178-1181`**  
Missing `s.replace(/'/g, '&#39;')`. Not exploitable in current usage (text nodes only), but incomplete.

### L17. escAttr() doesn't escape newlines or angle brackets
**`index.php:1182-1185`**  
A username containing `</div>` or `\n` could theoretically break out of the `onclick` attribute context. Low risk — TikTok usernames are alphanumeric.

### L18. Same-URL availability check can run twice
**`index.php:1019`**  
If `queueAvailCheck` is called twice for the same URL before the first completes, both are processed sequentially. Wasteful but not a functional bug.

### L19. Double browser notifications across tabs (Firefox)
**`index.php:814-837`**  
Both tabs independently detect `is_live && !wasLive` and create `new Notification()` with the same tag. Chrome deduplicates by tag across tabs; Firefox does not.

### L20. Availability check only examines HTTP status
**`index.php:1034-1053`**  
If TikTok's CDN returns 200 with an HTML error page body, the button shows green "available." Mitigated by the HEAD-vs-GET difference (proxy uses GET for the probe), but a 200 with wrong content is still "green."

## INFORMATIONAL (Positive findings)

### I1. Token comparison is timing-safe
All token comparisons use `hash_equals()` — no timing side-channel.

### I2. SSRF protection is solid
`proxy.php` validates URLs against `ALLOWED_CDN_HOSTS` and also validates redirect targets via `cdnRedirectAllowed()`. `api.php` never accepts user-controlled URLs.

### I3. No path traversal
No file access is controlled by user input.

### I4. No header injection
The `url` parameter goes to `CURLOPT_URL`, not `CURLOPT_HTTPHEADER`. PHP's `header()` rejects headers containing newlines.

### I5. Zombie worker protection is well-implemented
Three layers: `CURLOPT_LOW_SPEED_LIMIT/TIME` (20s stall guard), `connection_aborted()` checks (twice per chunk), and `ignore_user_abort(false)`.

### I6. Coverage log concurrency is safe
`FILE_APPEND | LOCK_EX` in `tests/lib/cov.php:58` — append-only with advisory locking. Duplicates are harmless (LCOV deduplicates).

### I7. No cross-request state leakage
Each PHP-FPM worker has independent memory. No shared caches or sessions.
